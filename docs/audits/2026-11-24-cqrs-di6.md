# Аудит CQRS 5 и совместимости с DI 6 — 2026-11-24

## Область и воспроизводимость

- Исходная ревизия CQRS: `5b4df0ef988004149376ac5953b936124c94e593`.
- Проверенная ревизия исходного кода: `2c4b9ffcdc818cbbcdfa626e8135c236b54ecc16`.
- DI 6: `2361c398fc938108de67df8ec6a723bf4c4648ff` (ветка `refactor/di6-definitions-callbacks`).
- Производственные ограничения Composer: PHP `^8.5.13`, DI `^6.0`. Временное разрешение dev-версии DI и локальный path repository существуют только в CI. Релиз CQRS не создан.
- Проверены основные маршруты command/query, операции, контекст, локаторы, резолверы, события, метаданные, нормализация карт, интеграция Config/DI, тестовое окружение и бенчмарки. Предусмотренная архитектура терминального обработчика QueryBus и делегирование invoker сохранены.
- Финальный прогон [CI](https://github.com/componenta/cqrs/actions/runs/45438029896): PHP 8.5.13 — 188 тестов, 472 assertions, PHPStan max без ошибок; PHP 8.6 — отдельный production consumer с минимальными зависимостями прошёл; 86 сценариев PHPBench в каждом из двух сравниваемых вариантов. Полный Pest на PHP 8.6 не запускался: несовместимость тестовых зависимостей и блокировка небезопасных версий Composer. Проверка безопасности не отключена.
- Мутационный прогон и полная проверка всех внешних интеграций в рамках этого этапа не выполнены. Это отчёт о проверенной ревизии, не сертификат отсутствия всех дефектов.

## Сохранение контрактов

- Operation и Context: один проход по атрибутам вместо отдельной проверки и копирования. Сохраняются проверка ключей, независимость от исходных ссылок верхнего уровня, shallow semantics, значения null и идентичность вложенных объектов. Завершение Operation использует clone-with PHP 8.5, сохраняет id, command, createdAt и исходные атрибуты, не разрешает повторную установку результата.
- Метаданные: ограниченный кеш (512 пар на провайдер), только ReflectionAttribute/отсутствие декларации в загруженном классе. Не кешируются недоступные классы и исключения. Конструктор атрибута выполняется при каждом get(), в том числе после неудачного создания. Сохранены исходные причины исключений, повторяемость атрибутов и обработка имён.
- Регистрации: убрана повторная валидация только там, где сами дескрипторы только что нормализованы. Валидация входящих извне карт сохраняется. Сохранены обнаружение конфликтов, дубликатов и детерминированный порядок.
- Composite resolvers: foreach прекращает перебор на первом поддерживающем делегате; fallback вызывается только после отказа остальных. Исключения не подавляются.
- CommandListenersLocator: индекс содержит только service id; разрешение сервиса остаётся ленивым и происходит через контейнер при каждом обходе. Порядок, множественные регистрации одного сервиса, wildcard и все три события проверены тестами.
- Реальный DI 6: обновление привязок обработчика, зависимостей и слушателя видно последующим вызовам. Из тестового bootstrap удалена неявная загрузка соседней рабочей копии DI.
- Проверка отчёта PHPBench контролирует количество сценариев каждого класса: устранено незаметное выпадение бенчмарков при обнаружении первого класса файла.

## Не внедрённые оптимизации и оставшийся задел

1. Не кешировать экземпляры сервисов, результат supports() произвольного резолвера или логическое имя только по классу сообщения: это ломает жизненный цикл DI и динамические контракты.
2. Не обходить invoker и не пропускать проверки входных карт. Не вводить общий singleton Context: это меняет наблюдаемую идентичность.
3. Для очень больших групп слушателей можно измерить гибридный индекс дубликатов в RegistrationNormalizer. Прямолинейная замена in_array на хеш-индекс ускоряет плотные группы, но изолированный эксперимент показал ухудшение распределённых групп; универсальную замену не внедряли.
4. Дополнительные copy-on-write оптимизации withAttribute/withoutAttribute и затраты cold-path метаданных — кандидаты для следующего отдельного сравнения; без измерений не менялись.
5. Значительная доля времени реального dispatch относится к вызову через DI; исследовать отдельно в DI 6, не разрушая контракт invoker.

## Релиз и интеграционные риски

- CQRS 5 имеет breaking changes по минимальным требованиям PHP и DI; существующий CQRS 4 остаётся отдельной линией релизов.
- Перед выпуском необходимо проверить фактически опубликованный DI 6, включая установку через обычный Composer без временной подмены, и повторить CI.
- Проверенные на дату аудита composer.json пакетов cqrs-app, cqrs-policy, cqrs-retry, cqrs-lock, cqrs-transaction-cycle, cqrs-transport и cqrs-transport-console ограничивают CQRS версией 4. cqrs-app также ограничивает DI версией 5. Они не обновлялись в этом аудите; требуется согласованная миграция интеграций и их тестов. Транспортные адаптеры дополнительно требуют проверки совместимости своей цепочки зависимостей.
- Внешняя зависимость cqrs-app от Internal\\RegistrationNormalizer должна быть решена при миграции интеграции как вопрос границы API, а не оптимизация.
- Семантика событий при исключении слушателя после исполнения обработчика и поведение retry/transaction остаются предметом существующего плана `docs/plans/cqrs-operation-lifecycle-contracts.md`. Произвольно менять гарантии доставки событий или повторного исполнения команды нельзя.
