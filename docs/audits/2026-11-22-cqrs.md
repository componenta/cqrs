## Reconstructed changes

- Attribute snapshots: `Context` and built-in `Operation` detach top-level references in caller-owned arrays while preserving object identity.
- Listener snapshots: `AsCommandListener` and normalized listener maps do not retain references from event-type arrays.
- Batch validation: explicit `null` for a selected command's attribute map is rejected before dispatch, while an absent entry still defaults to an empty array.
- Metadata: a leading namespace separator in an attribute class name is normalized before Reflection matching.
- Completed operation: built-in `Operation` with an existing result is rejected before locating or invoking a handler; unrelated `OperationInterface` implementations retain their own result semantics.
- Callable identity: string function targets are normalized to `Closure`; static method strings are normalized to callable arrays, preserving invoker scope and avoiding a second interpretation as a DI service identifier.
- New permanent regression coverage for the above and for registration conflict/error propagation/event stop conditions.
- Documentation and an invalid `LocatorCollector` example corrected.

See the Git history following `3e49a7d` for definitive diff and SHA attribution. These are deliberately separate from the inaccessible scratch history.

## Open architecture decision — CQRS-06: retry after processed-listener failure

**Evidence/sequence:** middleware topology `Retry → EventMiddleware → handler` can run the command body successfully, then receive a throwing `CommandProcessedEvent` listener. A retry around the whole event middleware may run the command body again even though the first attempt had side effects. The early completed-Operation guard does not solve this, because the outer retry may still hold the original operation without result. Whether the first attempt was committed depends on a separate transaction layer.

**Impact:** duplicate side effects, deliveries or writes if the command is not idempotent; caller might see an error despite a committed result.

**Alternatives:**
1. `EventMiddleware → Retry → handler` — one lifecycle event sequence per outer dispatch, with internal retry attempts invisible to these events.
2. `Retry → EventMiddleware → handler` — events per retry attempt; the retry policy must distinguish handler failures from post-handler notification failures to avoid an unsafe retry.
3. Transactional outbox for durable post-commit notifications, combined with idempotency and explicitly defined retry policies.

**Required product decisions:** Should lifecycle events describe a dispatch or each attempt? Are notifications transactional/durable? Which failures may retry the command body? Should exactly-once *effects* be protected by domain idempotency keys? Which optional retry/transaction middlewares does the application actually compose?

**Acceptance checks:** reproduce both middleware orders; assert handler count, event sequence and identity of propagated exceptions; test commit/rollback boundaries using real transaction integration; test notification failure and recovery; ensure no silent swallowing of domain failures. Do **not** add a new public exception/interface until a concrete integration requires it.

## Remaining non-blocking concerns and verification work

- Named function handler normalization creates a `Closure` each invocation. Historically observed microbenchmarks suggested a measurable cost with DI-aware reflection invokers, but this reconstruction did **not** re-run those benchmarks. Any caching optimization must preserve live DI dependencies, handler identity, magic-method scope, exception semantics, and mixed callable forms.
- Built-in `Operation` is immutable after a result is set; however dispatching the same unfinished operation concurrently can still run the handler multiple times. Idempotency is an application/domain concern unless a new operational contract is explicitly chosen.
- Attribute snapshots are shallow: nested reference containers, mutable object values and resources still have reference semantics. This is intentional compatibility, not a claim of deep immutability.
- `BatchCommandBus` prevalidates inputs but does not roll back earlier commands after a later handler failure.
- `cqrs-app` generated-map vs development-map parity, and the full integrations for retry/transaction/transport, were not re-audited in the current execution environment.
- The previous audit mentioned deprecations with an older `symfony/polyfill-php83` transitive dependency on minimal versions. That minimal-version matrix has not been repeated here.
